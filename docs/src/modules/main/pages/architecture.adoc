CerbIA evaluates loaded entries through a pipeline assembled by `Runner`. At
construction, `GateFactory` selects `SimpleGate` or `CascadeGate` from the
configuration. Both implement the `SecurityGate` protocol: one call evaluates
one entry and returns a `GateVerdict`. The runner combines loader output,
applies preprocessors, calls that shared protocol for each resulting entry, and
collects an overall `ScanResult`.

== Pipeline overview

The shared pipeline ends at the `SecurityGate` protocol. The configured
implementation determines how that entry is evaluated; both return the same
kind of verdict to `Runner`.

=== SimpleGate execution

`SimpleGate` routes each scanner by content type, runs compatible scanners in
order, and aggregates positive-risk BLOCK findings using each finding's
severity weight (`risk_score × severity.weight`); zero-risk and non-BLOCK
findings are excluded. The configured aggregator combines those scores. The
entry blocks when the aggregate reaches or exceeds the configured threshold;
without eligible positive BLOCK findings it allows, even at threshold `0`,
unless a blocking scanner failure occurred. With `fail_fast`, scanning can stop
at an individual non-negligible BLOCK finding whose weighted score reaches that
threshold, or at a blocking scanner failure; otherwise all eligible scanners
run. A known incompatible content type is skipped and recorded. Under scanner
error policy `fail`, the original scanner error propagates instead of producing
a verdict. See xref:gate.adoc[Gate behavior] for error details.

=== CascadeGate execution

`CascadeGate` evaluates ordered stages. All scanners in a reached stage
complete before its own positive weighted BLOCK findings are aggregated and
compared with that stage's thresholds, unless an operational fault interrupts
the stage. A terminal allow or block ends evaluation; defer advances to the
next stage. Later stages are not equivalent protection when an earlier stage
allows. Content-type mismatch is an operational fault, not a skip. See
xref:configuration.adoc[Configuration] for stage threshold inheritance and
decision boundaries.

== Construction and ownership

`Runner(config)` accepts a `SimpleGateConfig` or `CascadeGateConfig` and owns
pipeline assembly. It requires at least one loader. `GateFactory` dispatches on
the validated root variant once during construction, building a simple gate
with an ordered scanner list or a cascade with ordered stages. Component
instances are built through their factories.

Each component record supplies a fully-qualified class path and optional
`init_args`. Its factory imports the class, constructs it, and verifies that the
result satisfies the corresponding component contract. Factories construct
components; `Runner` owns their composition and execution order; the configured gate
owns evaluation of one entry. See xref:configuration.adoc[Configuration] for the
record format.

== Entry lifecycle

During a scan, loaders run in configuration order and their returned entry lists
are combined. Each preprocessor receives the complete current list, and its
returned list becomes the input to the next preprocessor. `Runner` calls
`SecurityGate.scan()` once for every final, post-preprocessing entry; the
selected implementation owns the internal evaluation topology.

=== Entry derivation and cardinality

An `Entry` contains text, source, an optional field path, metadata, and a
content type. `Entry.derive()` preserves source, field path, content type, and
copied metadata; it records the original text once and appends the preprocessor
identifier to the derivation lineage.

Current built-in preprocessors preserve one output entry per input entry. The
preprocessor extension contract does not guarantee that cardinality: extensions
may transform, remove, reorder, or expand entries. Results therefore correspond
to post-preprocessing entries, not necessarily to the original loaded entries.
See xref:components/loaders.adoc[Loaders] and
xref:components/preprocessors.adoc[Preprocessors] for component-specific behavior.

== Result hierarchy

Both implementations return a `GateVerdict` that `Runner` maps to the same
`EntryResult` shape. Simple results have `stages: null` and findings omit
`stage`. Cascade results include ordered stage summaries, and each executed
finding names its stage; all findings from executed stages appear once in the
flat findings list. Later stages after a terminal decision have
`result: not_reached`; they have no score.

|===
|Layer |Cardinality |Responsibility

|`GateVerdict` |One per scanned entry |Gate safety, score, rationale, findings, and topology-specific skips or stage summaries.
|`EntryResult` |One per post-preprocessing entry |Associates the entry with its gate result.
|`ScanResult` |One per runner scan |Collects entry results and computes summary fields.
|===

`ScanResult.is_safe` is true only when every entry result is safe.
`total_findings` and `unsafe_entries` summarize all entry results. A configured
loader can return no entries; in that case the gate is not called and the empty
`ScanResult` is safe with zero findings and unsafe entries. This does not relax
construction requirements for configured loaders and scanners.

== Shared URL registry

While constructing scanners, `GateFactory` creates one `UrlRegistry` for that runner
instance and passes it through scanner factories to allowlist, denylist, and
malicious-URL scanners. The registry keeps allow and deny patterns separately;
an explicit deny takes precedence over a matching allow rule, independent of
registration order. Separate runners use separate registries; this is neither
global state nor a general dependency container.

See xref:components/scanners.adoc[Scanners] for scanner-specific URL behavior.
